# Testing Guide for Rallycross Driver Rankings

## Overview

This project includes comprehensive unit and integration tests using **pytest**. The test suite covers:

- **42 test cases** organized into 8 test classes
- **56% code coverage** of the main runner module
- Unit tests for all core classes (Driver, DriverPair, DriverCollection, Runner)
- Integration tests for the full data pipeline
- Edge case and boundary condition testing
- Accuracy level categorization testing

## Test Structure

### Test Classes

1. **TestAccuracyLevel** (4 tests)
   - Tests the `get_accuracy_level()` function
   - Verifies accuracy categorization: low (<10), medium (10-19), high (20+)
   - Tests boundary conditions at thresholds

2. **TestDriver** (6 tests)
   - Tests Driver class creation and basic operations
   - Verifies name formatting, initialization, and data aggregation
   - Tests event counting and performance metrics

3. **TestDriverPair** (6 tests)
   - Tests DriverPair class for storing driver comparisons
   - Verifies time difference calculations (raw and normalized)
   - Tests dictionary conversion for CSV export
   - Edge case: zero baseline handling

4. **TestDriverCollection** (10 tests)
   - Tests collection creation, adding drivers, deduplication
   - Tests search methods: get_by_name(), get_by_class(), get_all_classes()
   - Tests driver ID generation and retrieval

5. **TestRunner** (5 tests)
   - Tests Runner instance creation with various parameters
   - Tests recency weight calculation with exponential decay
   - Tests weighted average diff calculation

6. **TestIntegration** (5 tests)
    - Full pipeline tests with sample race data
    - Tests building class graphs from pairwise comparisons
    - Tests cross-class ranking generation
    - Tests CSV export functionality to output/ directory
    - Automatic setup_output_dir fixture for output directory management

7. **TestEdgeCases** (6 tests)
    - Tests driver names with special characters
    - Tests multi-word last names (e.g., "Diego De")
    - Tests identical times in driver pairs
    - Tests nonexistent class lookups
    - Tests negative values and empty data

## Running Tests

### Run All Tests
```bash
python3 -m pytest test_runner.py -v
```

### Run Specific Test Class
```bash
python3 -m pytest test_runner.py::TestDriver -v
```

### Run Specific Test
```bash
python3 -m pytest test_runner.py::TestDriver::test_driver_name -v
```

### Run with Coverage Report
```bash
python3 -m pytest test_runner.py --cov=runner --cov-report=term-missing
```

### Generate HTML Coverage Report
```bash
python3 -m pytest test_runner.py --cov=runner --cov-report=html
```

### Run Tests by Marker
```bash
python3 -m pytest test_runner.py -m unit
python3 -m pytest test_runner.py -m integration
python3 -m pytest test_runner.py -m edge_case
```

## Test Data

Tests use two types of test data:

### Output Directory Management

The `setup_output_dir` fixture (autouse=True) is applied to all tests in TestIntegration:
- **Before each test**: Creates the `output/` directory and removes any existing CSV files
- **After each test**: Cleans up CSV files to ensure test isolation

This ensures:
- Tests don't interfere with each other
- Output directory is always in a clean state
- CSV files generated by tests don't accumulate

### Fixtures
- `runner`: A basic Runner instance with default parameters
- `sample_records`: 5 sample race records across 2 classes (MA, PR)
- `temp_results_dir`: Temporary directory for file I/O tests
- `setup_output_dir`: Automatically creates and cleans the output/ directory before and after each test

### Sample Records Format

```python
}
```

```python
def test_full_pipeline(self, sample_records):
    """Test the complete runner pipeline with sample data."""
    runner = Runner(runtime=60.0, depth=1)
    runner.records = sample_records
    
    # Add drivers and build comparisons

        runner.drivers.add(record['first_name'], record['last_name'], record['class'])
    
    # Verify pipeline results
```

## Best Practices

1. **Test Isolation**: Each test is independent and can run in any order
2. **Fixtures**: Reusable test data setup via pytest fixtures
3. **Clarity**: Descriptive test names and docstrings explain intent
4. **Coverage**: Tests verify both happy path and edge cases
5. **Speed**: All tests run in under 1 second

## Adding New Tests

When adding features, follow these guidelines:

1. Write a failing test first (TDD approach)
2. Group related tests into a test class
3. Use descriptive names: `test_<what>_<scenario>`
4. Add docstrings explaining what is being tested
5. Use fixtures for common setup
6. Include both positive and negative test cases

Example template:

```python
class TestNewFeature:
    """Test the new feature."""
    
    def test_new_feature_works(self):
        """Test that the feature works correctly."""
        # Arrange
        obj = NewClass()
        
        # Act
        result = obj.new_method()
        
        # Assert
        assert result == expected_value
    
    def test_new_feature_edge_case(self):
        """Test edge case handling."""
        # Test boundary conditions
        assert obj.new_method(edge_value) == expected_edge_result
```

## Troubleshooting

### Import Errors
```bash
# Ensure runner.py is in the same directory
# or add to PYTHONPATH
export PYTHONPATH="${PYTHONPATH}:$(pwd)"
```

### Test Not Found
```bash
# Make sure test file is named test_*.py
# and test class/method follow naming convention
python3 -m pytest test_runner.py --collect-only
```

### Coverage Not Calculated
```bash
# Install pytest-cov if not already installed
python3 -m pip install pytest-cov --break-system-packages
```
